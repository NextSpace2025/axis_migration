# Axis Migration 워크플로우

상태: 확정 전 초안 · 2026-11-27
이 문서에서 워크플로우를 확정한 뒤, 이를 기준으로 MCP 도구와 코드 구조를 정합니다.

## 한 줄 요약

Claude가 **tenant(회사)의 규칙**을 불러와 문서를 해석합니다.
규칙은 그 회사가 속한 **업종의 그릇** 안에서 만들어집니다.
처음 한 번은 사용자가 표 구성과 헤더를 확정합니다. 그 뒤로는 확정된 규칙에 맞춰 새 파일을 계속 재배치하고 사이트에 배포합니다.

## 개념 구조

```
Axis Migration (도구: 회사·업종과 무관)
│
├─ 업종 그릇: 건설                      ← 지금 있는 유일한 그릇
│  ├─ 기본 모델: 문서 종류, 공통 표·헤더, 수량·단위·금액 규칙, 검증 규칙
│  │  (construction-schema-design / data-migration / document-matching 스킬)
│  │
│  ├─ tenant: 익진엔지니어링             ← 지금 있는 유일한 tenant
│  │  ├─ 규칙 v1: 표 구성, 헤더, 분류 체계(T1~T7 업체 유형 등), 매핑 규칙, 확정 예시
│  │  ├─ 규칙 v2 …
│  │  └─ 결과: 규칙 버전별로 배치·배포한 데이터
│  │
│  └─ tenant: (다른 건설사) …
│
└─ 업종 그릇: (제조, 유통 …)            ← 나중에 추가
   ├─ 기본 모델
   └─ tenant …
```

| 층 | 무엇인가 | 누가 정하나 | 어디에 두나 |
|---|---|---|---|
| 도구 | 단계 진행, 검증, 배포, 화면 | Axis 개발 | 이 저장소 (공개) |
| 업종 그릇 | 그 업종 문서를 담는 기본 모델과 공통 규칙 | Axis 개발 | 이 저장소 (공개, 회사 데이터 없음) |
| tenant 규칙 | 그 회사만의 표 구성, 헤더, 분류, 매핑 | 그 회사 사용자가 확정 | tenant 저장소 (비공개) |
| 결과 | 규칙을 적용해 배치한 데이터 | 자동 생성, 검증 후 배포 | tenant 저장소 (비공개) |

- tenant 규칙은 업종 그릇을 기반으로 만들고, 그 위에 회사별로 더하거나 바꿉니다.
- tenant 저장소의 실제 구현(현재 사용 중인 DB 등)은 이 문서에서 정하지 않습니다. 도구는 "tenant 규칙 읽기·저장, 결과 배포" 인터페이스로만 접근합니다.
- 회사별 규칙과 데이터는 공개 저장소에 넣지 않습니다.

## 등장 요소

| 요소 | 역할 |
|---|---|
| 사용자 | 요청하고, 표 구성과 헤더를 확정하고, 사이트에서 결과를 봅니다 |
| Claude | **유일하게 해석하는 AI**입니다. 업종 그릇과 tenant 규칙을 참고해 문서를 읽고, 구조를 제안하고, 배치합니다 |
| Axis MCP | tenant 규칙을 불러오고 저장합니다. 단계를 진행하고, 결과를 검증하고, 배포합니다. AI는 없습니다 |
| tenant 저장소 | tenant별 규칙(버전)과 배포된 결과를 보관합니다 |
| 웹 사이트 | 조회 코드로 tenant의 결과 표를 봅니다 |

## 흐름 1. 처음: tenant 규칙 만들기와 확정

```
사용자: "axis migration으로 익진엔지니어링 양식에 맞춰서 <폴더> 가져와줘"
  │
  ├─ 1. MCP: tenant "익진엔지니어링" 조회 → 업종(건설) 그릇 확인, 규칙 없음 (또는 초안)
  ├─ 2. Claude: 건설 그릇의 기본 모델을 바탕으로 폴더의 실제 문서를 해석
  │         → 대략적인 표 구성과 헤더 제안 (원문 근거 포함)
  ├─ 3. 사용자: 검토 화면에서 표와 헤더를 수정·확정
  ├─ 4. MCP: 확정 구조를 익진엔지니어링 규칙 v1로 저장
  ├─ 5. Claude: 규칙 v1로 전체 파일을 다시 해석해 배치 → SQLite
  ├─ 6. MCP: 검증 (원본 불변, 확정 구조 일치, 수량·금액, 무결성)
  └─ 7. MCP: 배포 → 조회 코드와 사이트 주소 반환
```

## 흐름 2. 반복: 확정 규칙으로 재배치

```
사용자: "axis migration으로 익진엔지니어링 양식에 맞춰서 <새 폴더 또는 새 파일> 가져와줘"
  │
  ├─ 1. MCP: 익진엔지니어링 규칙 최신 확정 버전 로드
  ├─ 2. Claude: 규칙에 맞춰 파일을 해석하고 배치 (구조 검토 생략)
  │         → 규칙에 맞지 않는 파일이나 헤더는 보류 목록으로 분리
  ├─ 3. MCP: 검증
  └─ 4. MCP: 배포 → 사이트에서 확인
```

보류 목록이 생기면 흐름 1의 2~4단계처럼 규칙 개정안을 제안하고 확정합니다. 확정되면 v2가 됩니다.

## 흐름 3. 새 tenant 또는 새 업종

- **같은 업종의 새 회사:** tenant를 만들고 업종 그릇을 지정한 뒤 흐름 1을 진행합니다.
- **새 업종:** 먼저 업종 그릇(기본 모델, 공통 규칙)을 만들어야 합니다. Axis 개발 작업이고, 회사 데이터 없이 공개 저장소에 추가합니다.

## 지켜야 할 원칙 (현재 스킬 규칙 유지)

- 원본 파일은 읽기만 하고 수정하거나 옮기지 않습니다.
- 수량, 금액, 단위는 원문 그대로 보존하고, 각 행에 출처 위치를 남깁니다.
- 대표 샘플만 보고 전체를 처리했다고 판단하지 않습니다. 모든 파일의 처리 결과를 기록합니다.
- tenant 규칙과 결과는 공개 저장소에 넣지 않고, tenant끼리 섞이지 않게 합니다.
- 배포는 검증을 통과한 결과만 합니다.
- **규칙과 검증은 호출하는 쪽과 무관하게 같습니다.** Claude, Codex, CLI 중 무엇으로 호출해도 같은 스킬과 같은 tenant 규칙을 쓰고, 같은 검증을 거칩니다. 검증은 호출하는 에이전트가 아니라 Axis가 단계를 넘길 때(제출 시점) 직접 실행하므로, 어떤 경로로도 건너뛸 수 없습니다.

## 현재 상태와의 차이

| 개념 | 지금 | 목표 |
|---|---|---|
| 업종 그릇 | 건설 스킬 3개가 있지만, 그릇이라는 경계 없이 도구에 섞여 있음 | 업종 단위로 분리 |
| tenant | 없음. 실행마다 기준 회사 이름만 받음 | tenant 단위로 규칙과 결과를 묶음 |
| tenant 규칙 | 익진엔지니어링 기준이 도구 밖의 Claude 스킬(`billing-to-db`, `construction-cost-classifier`)에만 있음 | tenant 저장소에 버전으로 보관 |
| 확정 구조 | `approved-schema.json`이 실행 폴더 하나에서만 쓰임 | tenant 규칙 버전으로 저장해 재사용 |
| 결과 | 데이터셋마다 따로 있고, 어떤 규칙으로 만들었는지 기록 없음 | tenant와 규칙 버전을 기록 |

## 확정이 필요한 질문

1. **익진엔지니어링 규칙의 시작점:** `billing-to-db`(REV.4.3.2.1 헤더)와 `construction-cost-classifier`(T1~T7 분류)를 규칙 v1의 출발점으로 옮기면 될까요?
2. **반복 배치 결과:** tenant의 같은 장부에 계속 누적하나요, 아니면 배치마다 새 조회 코드를 만드나요?
3. **규칙에 없는 문서:** 반복 중 새로운 문서 종류가 나오면 그 파일만 보류하고 나머지는 배포하나요, 아니면 규칙을 개정할 때까지 전체를 멈추나요?
4. **원본 위치:** 원본은 서버의 로컬 폴더에만 있나요, 아니면 사이트에서 업로드하는 경로도 필요한가요?
5. **배포 전 확인:** 반복 배치는 검증만 통과하면 자동으로 배포하나요, 아니면 매번 사용자가 확인하나요?
6. **규칙 관리 권한:** tenant 규칙을 확정하거나 개정할 수 있는 사람은 누구이며, 이전 버전으로 되돌릴 수 있어야 하나요?

## 확정된 사항

- **T1~T7 업체 유형은 익진엔지니어링의 tenant 규칙입니다.** 건설 업종 그릇에는 넣지 않습니다. 그릇에는 업체 유형을 담을 자리(분류 체계 슬롯)만 두고, 유형의 정의와 값은 tenant 규칙에서 정합니다.
